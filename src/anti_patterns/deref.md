# พอลิมอร์ฟิซึมผ่าน `Deref`

## คำอธิบาย

ใช้ trait `Deref` อย่างผิดวัตถุประสงค์เพื่อเลียนแบบการสืบทอด (inheritance) ระหว่าง struct แล้วใช้เมท็อดร่วมกัน

## ตัวอย่าง

บางครั้งเราต้องการเลียนแบบแพตเทิร์นที่พบบ่อยในภาษา OO อย่าง Java ดังนี้:

```java
class Foo {
    void m() { ... }
}

class Bar extends Foo {}

public static void main(String[] args) {
    Bar b = new Bar();
    b.m();
}
```

เราใช้แอนติแพตเทิร์นพอลิมอร์ฟิซึมผ่าน deref ทำได้ดังนี้:

```rust
use std::ops::Deref;

struct Foo {}

impl Foo {
    fn m(&self) {
        //..
    }
}

struct Bar {
    f: Foo,
}

impl Deref for Bar {
    type Target = Foo;
    fn deref(&self) -> &Foo {
        &self.f
    }
}

fn main() {
    let b = Bar { f: Foo {} };
    b.m();
}
```

Rust ไม่มีการสืบทอด struct เราจึงใช้การประกอบ (composition) โดยใส่อินสแตนซ์ของ `Foo` ไว้ใน `Bar` (เนื่องจากฟิลด์เป็นค่า มันจึงถูกเก็บแบบอินไลน์ ดังนั้นหากมีฟิลด์อื่น เลย์เอาต์ในหน่วยความจำก็จะเหมือนกับเวอร์ชัน Java (อาจจะนะ คุณควรใช้ `#[repr(C)]` หากต้องการแน่ใจ))

เพื่อให้การเรียกเมท็อดทำงานได้ เราอิมพลีเมนต์ `Deref` ให้ `Bar` โดยมี `Foo` เป็นเป้าหมาย (คืนฟิลด์ `Foo` ที่ฝังอยู่) นั่นหมายความว่าเมื่อเราดึงค่าอ้างอิงจาก `Bar` (ตัวอย่างเช่น ใช้ `*`) เราจะได้ `Foo` ซึ่งค่อนข้างแปลก การดึงค่าอ้างอิงปกติให้ `T` จากเรฟเฟอเรนซ์ไปยัง `T` แต่ตรงนี้เรามีชนิดข้อมูลสองชนิดที่ไม่เกี่ยวข้องกัน อย่างไรก็ตาม เนื่องจากโอเปอเรเตอร์จุด (dot) ทำการดึงค่าอ้างอิงโดยนัย การเรียกเมท็อดจึงค้นหาเมท็อดบน `Foo` รวมทั้งบน `Bar` ด้วย

## ข้อดี

ประหยัดโค้ด boilerplate ไปเล็กน้อย เช่น

```rust,ignore
impl Bar {
    fn m(&self) {
        self.f.m()
    }
}
```

## ข้อเสีย

ที่สำคัญที่สุดคือ นี่เป็นสำนวนที่น่าประหลาดใจ - โปรแกรมเมอร์ในอนาคตที่อ่านโค้ดนี้จะไม่คาดคิดว่าจะเกิดสิ่งนี้ขึ้น เพราะเราใช้ trait `Deref` ผิดวัตถุประสงค์ แทนที่จะใช้ตามที่ตั้งใจ (และตามที่เอกสารระบุ ฯลฯ) อีกทั้งกลไกตรงนี้ยังเป็นโดยนัยอย่างสมบูรณ์

แพตเทิร์นนี้ไม่ได้สร้างความสัมพันธ์แบบชนิดย่อย (subtyping) ระหว่าง `Foo` กับ `Bar` เหมือนการสืบทอดใน Java หรือ C++ ยิ่งไปกว่านั้น trait ที่ `Foo` อิมพลีเมนต์จะไม่ถูกอิมพลีเมนต์ให้ `Bar` โดยอัตโนมัติ แพตเทิร์นนี้จึงเข้ากันได้ไม่ดีกับการตรวจสอบขอบเขตและการเขียนโปรแกรมเจเนอริก

การใช้แพตเทิร์นนี้ให้ความหมายเชิงความหมายต่อ `self` ที่ต่างจากภาษา OO ส่วนใหญ่เล็กน้อย โดยปกติ `self` ยังคงเป็นการอ้างอิงถึงคลาสย่อย แต่กับแพตเทิร์นนี้มันจะเป็น 'คลาส' ที่เมท็อดถูกนิยามไว้

สุดท้าย แพตเทิร์นนี้รองรับการสืบทอดเดี่ยวเท่านั้น และไม่มีแนวคิดเรื่องอินเทอร์เฟซ ความเป็นส่วนตัวระดับคลาส หรือฟีเจอร์อื่นๆ ที่เกี่ยวกับการสืบทอด จึงให้ประสบการณ์ที่สร้างความประหลาดใจเล็กๆ แก่โปรแกรมเมอร์ที่คุ้นเคยกับการสืบทอดใน Java เป็นต้น

## การอภิปราย

ไม่มีทางเลือกเดียวที่ดี ขึ้นอยู่กับสถานการณ์ที่แน่นอน อาจดีกว่าที่จะอิมพลีเมนต์ใหม่ด้วย traits หรือเขียนเมท็อด facade เพื่อส่งต่อไปยัง `Foo` ด้วยตนเอง เราตั้งใจจะเพิ่มกลไกการสืบทอดที่คล้ายคลึงนี้ให้ Rust แต่คงต้องใช้เวลาอีกระยะกว่าจะถึง stable Rust ดู[บล็อก](http://aturon.github.io/blog/2015/09/18/reuse/)
[โพสต์](http://smallcultfollowing.com/babysteps/blog/2015/10/08/virtual-structs-part-4-extended-enums-and-thin-traits/)
และ [RFC issue](https://github.com/rust-lang/rfcs/issues/349) นี้สำหรับรายละเอียดเพิ่มเติม

trait `Deref` ถูกออกแบบมาสำหรับการอิมพลีเมนต์ชนิดพอยน์เตอร์ที่กำหนดเอง เจตนาคือให้มันรับพอยน์เตอร์ไปยัง `T` แล้วได้ `T` ไม่ใช่แปลงระหว่างชนิดที่ต่างกัน น่าเสียดายที่สิ่งนี้ไม่ได้ถูก (และคงเป็นไปไม่ได้ที่จะถูก) บังคับโดยนิยามของ trait

Rust พยายามสร้างสมดุลอย่างระมัดระวังระหว่างกลไกแบบชัดเจนและแบบโดยนัย โดยเอนไปทางเอียงการแปลงระหว่างชนิดที่ชัดเจน การดึงค่าอ้างอิงอัตโนมัติในโอเปอเรเตอร์จุดเป็นกรณีที่ความสะดวกสนับสนุนกลไกแบบโดยนัยอย่างมาก แต่เจตนาคือให้จำกัดเพียงระดับของการอ้อมผ่าน ไม่ใช่การแปลงระหว่างชนิดใดๆ
