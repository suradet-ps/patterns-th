# การรวมชนิดเข้าเป็นตัวห่อ

## คำอธิบาย

แพตเทิร์นนี้ออกแบบมาเพื่อให้จัดการกับชนิดข้อมูลที่เกี่ยวข้องกันหลายชนิดได้อย่างราบรื่น ขณะเดียวกันก็ลดพื้นที่ผิวของความไม่ปลอดภัยด้านหน่วยความจำ (memory unsafety) ให้เหลือน้อยที่สุด

หนึ่งในเสาหลักของกฎการตั้งฉายา (aliasing rules) ของ Rust คือไลฟ์ไทม์ สิ่งนี้รับประกันว่ารูปแบบการเข้าถึงระหว่างชนิดข้อมูลหลายๆ แบบสามารถปลอดภัยต่อหน่วยความจำ รวมถึงปลอดภัยจาก data race ด้วย

อย่างไรก็ตาม เมื่อชนิดข้อมูล Rust ถูกส่งออกไปยังภาษาอื่น มักถูกแปลงเป็นพอยน์เตอร์ ใน Rust พอยน์เตอร์หมายความว่า "ผู้ใช้ดูแลอายุการใช้งานของสิ่งที่ถูกชี้" เป็นความรับผิดชอบของผู้ใช้ที่จะหลีกเลี่ยงความไม่ปลอดภัยด้านหน่วยความจำ

ด้วยเหตุนี้จึงจำเป็นต้องมีความเชื่อมั่นต่อโค้ดผู้ใช้ในระดับหนึ่ง โดยเฉพาะในเรื่อง use-after-free ซึ่ง Rust ทำอะไรไม่ได้เลย อย่างไรก็ตาม การออกแบบ API บางแบบสร้างภาระให้กับโค้ดที่เขียนในภาษาอื่นมากกว่าแบบอื่น

API ที่มีความเสี่ยงต่ำที่สุดคือ "ตัวห่อแบบรวม (consolidated wrapper)" ซึ่งการปฏิสัมพันธ์กับออบเจกต์ที่เป็นไปได้ทั้งหมดถูกรวมเข้าเป็น "ชนิดตัวห่อ" ขณะที่ API ฝั่ง Rust ยังคงสะอาด

## ตัวอย่างโค้ด

เพื่อให้เข้าใจ ลองดูตัวอย่างคลาสสิกของ API ที่ต้องส่งออก: การวนซ้ำผ่านคอลเลกชัน

API นั้นมีหน้าตาดังนี้:

1. อิเทอเรเตอร์ถูกเริ่มต้นด้วย `first_key`
2. ทุกครั้งที่เรียก `next_key` อิเทอเรเตอร์จะเลื่อนไปข้างหน้า
3. การเรียก `next_key` ขณะที่อิเทอเรเตอร์อยู่ที่จุดสิ้นสุดจะไม่ทำอะไร
4. ตามที่กล่าวข้างต้น อิเทอเรเตอร์ถูก "ห่อเข้าไปใน" คอลเลกชัน (ต่างจาก API แบบ
   Rust พื้นเมือง)

หากอิเทอเรเตอร์อิมพลีเมนต์ `nth()` อย่างมีประสิทธิภาพ ก็เป็นไปได้ที่จะทำให้มันมีอายุเพียงชั่วคราวต่อการเรียกฟังก์ชันหนึ่งครั้ง:

```rust,ignore
struct MySetWrapper {
    myset: MySet,
    iter_next: usize,
}

impl MySetWrapper {
    pub fn first_key(&mut self) -> Option<&Key> {
        self.iter_next = 0;
        self.next_key()
    }
    pub fn next_key(&mut self) -> Option<&Key> {
        if let Some(next) = self.myset.keys().nth(self.iter_next) {
            self.iter_next += 1;
            Some(next)
        } else {
            None
        }
    }
}
```

ผลก็คือตัวห่อเรียบง่ายและไม่มีโค้ด `unsafe` เลย

## ข้อดี

วิธีนี้ทำให้ API ปลอดภัยต่อการใช้งานมากขึ้น หลีกเลี่ยงปัญหาเรื่องไลฟ์ไทม์ระหว่างชนิดข้อมูล ดู
[API แบบอิงออบเจกต์](./export.md) สำหรับข้อดีและหลุมพรางที่วิธีนี้หลีกเลี่ยง

## ข้อเสีย

บ่อยครั้ง การห่อชนิดข้อมูลเป็นเรื่องยากทีเดียว และบางครั้งการประนีประนอมกับ API ฝั่ง Rust ก็ทำให้ทุกอย่างง่ายขึ้น

ตัวอย่างเช่น ลองพิจารณาอิเทอเรเตอร์ที่อิมพลีเมนต์ `nth()` อย่างไม่มีประสิทธิภาพ การเพิ่มตรรกะพิเศษเพื่อให้ออบเจกต์จัดการการวนซ้ำภายในเอง หรือรองรับรูปแบบการเข้าถึงแบบอื่นที่มีประสิทธิภาพซึ่งมีเพียง Foreign Function API เท่านั้นที่จะใช้ คงคุ้มค่าอย่างแน่นอน

### ลองห่ออิเทอเรเตอร์ (และล้มเหลว)

การห่ออิเทอเรเตอร์ชนิดใดก็ได้เข้าใน API อย่างถูกต้อง ตัวห่อจะต้องทำสิ่งที่โค้ดเวอร์ชัน C ทำ นั่นคือลบไลฟ์ไทม์ของอิเทอเรเตอร์ทิ้งแล้วจัดการด้วยตนเอง

พูดสั้นๆ ก็คือ เรื่องนี้*ยากสุดๆ*

นี่คือภาพประกอบของหลุมพรางเพียง*หนึ่ง*ข้อ

`MySetWrapper` เวอร์ชันแรกจะมีหน้าตาดังนี้:

```rust,ignore
struct MySetWrapper {
    myset: MySet,
    iter_next: usize,
    // created from a transmuted Box<KeysIter + 'self>
    iterator: Option<NonNull<KeysIter<'static>>>,
}
```

เมื่อใช้ `transmute` เพื่อยืดไลฟ์ไทม์ และใช้พอยน์เตอร์เพื่อซ่อนมัน มันก็ดูน่าเกลียดอยู่แล้ว แต่ยังแย่กว่านั้นอีก: *การดำเนินการอื่นใดก็ทำให้เกิด Rust `undefined behaviour` ได้*

ลองพิจารณาว่า `MySet` ในตัวห่ออาจถูกฟังก์ชันอื่นจัดการระหว่างการวนซ้ำ เช่น การเก็บค่าใหม่ลงในคีย์ที่กำลังวนซ้ำอยู่ API ไม่ได้ห้ามสิ่งนี้ และอันที่จริงไลบรารี C ที่คล้ายกันบางตัวก็คาดหวังพฤติกรรมนี้

การอิมพลีเมนต์ `myset_store` อย่างง่ายจะมีหน้าตาดังนี้:

```rust,ignore
pub mod unsafe_module {

    // other module content

    pub fn myset_store(myset: *mut MySetWrapper, key: datum, value: datum) -> libc::c_int {
        // DO NOT USE THIS CODE. IT IS UNSAFE TO DEMONSTRATE A PROBLEM.

        let myset: &mut MySet = unsafe {
            // SAFETY: whoops, UB occurs in here!
            &mut (*myset).myset
        };

        /* ...check and cast key and value data... */

        match myset.store(casted_key, casted_value) {
            Ok(_) => 0,
            Err(e) => e.into(),
        }
    }
}
```

หากอิเทอเรเตอร์ยังอยู่ตอนที่ฟังก์ชันนี้ถูกเรียก เราได้ละเมิดกฎการตั้งฉายาของ Rust ข้อหนึ่ง ตามกฎของ Rust เรฟเฟอเรนซ์ที่แก้ไขได้ในบล็อกนี้ต้องเข้าถึงออบเจกต์แบบ*เอกสิทธิ์* (exclusive) หากอิเทอเรเตอร์เพียงแค่ยังอยู่ มันก็ไม่ใช่เอกสิทธิ์ เราจึงมี `undefined behaviour`! [^1]

เพื่อหลีกเลี่ยงสิ่งนี้ เราต้องมีวิธีรับประกันว่าเรฟเฟอเรนซ์ที่แก้ไขได้นั้นเป็นเอกสิทธิ์จริงๆ ซึ่งโดยพื้นฐานหมายถึงการล้างเรฟเฟอเรนซ์แบบใช้ร่วมของอิเทอเรเตอร์ออกขณะที่มันยังอยู่ แล้วสร้างมันขึ้นใหม่ ในกรณีส่วนใหญ่ วิธีนั้นก็ยังมีประสิทธิภาพน้อยกว่าเวอร์ชัน C อยู่ดี

บางคนอาจถามว่า แล้ว C ทำแบบนี้ได้มีประสิทธิภาพกว่าได้อย่างไร? คำตอบคือ มันโกง กฎการตั้งฉายาของ Rust คือตัวปัญหา และ C ก็เพียงแค่เพิกเฉยต่อกฎเหล่านั้นสำหรับพอยน์เตอร์ของมัน เป็นการแลกเปลี่ยน เราจึงมักเห็นโค้ดที่ประกาศในคู่มือว่า "ไม่ปลอดภัยต่อเธรด" ในบางหรือทุกสถานการณ์ อันที่จริง
[ไลบรารี GNU C](https://manpages.debian.org/buster/manpages/attributes.7.en.html)
มีคำศัพท์ทั้งชุดที่อุทิศให้กับพฤติกรรมแบบพร้อมกัน (concurrent)!

Rust ยอมทำให้ทุกอย่างปลอดภัยต่อหน่วยความจำตลอดเวลา ทั้งเพื่อความปลอดภัยและเพื่อการ optimize ที่โค้ด C ทำไม่ได้ การถูกปฏิเสธไม่ให้ใช้ทางลัดบางอย่างคือราคาที่โปรแกรมเมอร์ Rust ต้องจ่าย

[^1]: สำหรับโปรแกรมเมอร์ C ที่กำลังเกาหัวอยู่ อิเทอเรเตอร์ไม่จำเป็นต้องถูกอ่าน*ระหว่าง*โค้ดนี้เพื่อก่อให้เกิด UB กฎเอกสิทธิ์ยังเปิดทางให้คอมไพเลอร์ optimize ซึ่งอาจทำให้การสังเกตผ่านเรฟเฟอเรนซ์แบบใช้ร่วมของอิเทอเรเตอร์ไม่สอดคล้องกัน (เช่น stack spill หรือการเรียงคำสั่งใหม่เพื่อประสิทธิภาพ) การสังเกตเหล่านี้อาจเกิดขึ้น*เมื่อใดก็ได้หลังจาก*เรฟเฟอเรนซ์ที่แก้ไขได้ถูกสร้างขึ้น
