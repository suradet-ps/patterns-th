# API แบบอิงออบเจกต์

## คำอธิบาย

เมื่อออกแบบ API ใน Rust ที่เปิดเผยให้ภาษาอื่นใช้ มีหลักการออกแบบสำคัญบางข้อที่ตรงข้ามกับการออกแบบ API Rust ทั่วไป:

1. ชนิดข้อมูลที่ห่อหุ้ม (Encapsulated) ทั้งหมดควรเป็น*เจ้าของ*โดย Rust
   *จัดการ*โดยผู้ใช้ และ*ทึบแสง* (opaque)
2. ชนิดข้อมูลที่ใช้แลกเปลี่ยน (Transactional) ทั้งหมดควรเป็น*เจ้าของ*โดยผู้ใช้
   และ*โปร่งใส* (transparent)
3. พฤติกรรมทั้งหมดของไลบรารีควรเป็นฟังก์ชันที่ทำงานบนชนิด Encapsulated
4. พฤติกรรมทั้งหมดของไลบรารีควรถูกห่อหุ้มเข้าเป็นชนิดข้อมูลโดยยึดตาม
   *แหล่งที่มา/ไลฟ์ไทม์* ไม่ใช่ยึดตามโครงสร้าง

## แรงจูงใจ

Rust มีการรองรับ FFI ไปยังภาษาอื่นในตัว โดยเปิดช่องให้ผู้เขียนครีตนำเสนอ API ที่เข้ากันได้กับ C ผ่าน ABI ต่างๆ (แม้เรื่องนั้นจะไม่สำคัญต่อแนวปฏิบัตินี้)

Rust FFI ที่ออกแบบมาอย่างดีจะทำตามหลักการออกแบบ API ของ C ขณะเดียวกันก็ประนีประนอมกับการออกแบบฝั่ง Rust ให้น้อยที่สุด มีเป้าหมายสามข้อสำหรับ API ต่างภาษาใดๆ:

1. ใช้งานง่ายในภาษาเป้าหมาย
2. หลีกเลี่ยงไม่ให้ API กำหนดความไม่ปลอดภัยภายในฝั่ง Rust ให้น้อยที่สุดเท่าที่จะทำได้
3. รักษาความเสี่ยงต่อความไม่ปลอดภัยด้านหน่วยความจำและ Rust `undefined behaviour` ให้น้อยที่สุด

โค้ด Rust ต้องเชื่อมั่นในความปลอดภัยด้านหน่วยความจำของภาษาต่างภาษาถึงจุดหนึ่ง อย่างไรก็ตาม ทุกส่วนของโค้ด `unsafe` ฝั่ง Rust ล้วนเป็นโอกาสให้เกิดบั๊ก หรือทำให้ `undefined behaviour` รุนแรงขึ้น

ตัวอย่างเช่น หากแหล่งที่มาของพอยน์เตอร์ผิด อาจเกิด segfault จากการเข้าถึงหน่วยความจำที่ไม่ถูกต้อง แต่หากมันถูกจัดการโดยโค้ด unsafe ก็อาจกลายเป็นความเสียหายของฮีปเต็มรูปแบบได้

การออกแบบ API แบบอิงออบเจกต์ช่วยให้เขียนตัวเชื่อม (shim) ที่มีคุณสมบัติความปลอดภัยด้านหน่วยความจำที่ดี และมีขอบเขตชัดเจนว่าส่วนใดปลอดภัยและส่วนใด `unsafe`

## ตัวอย่างโค้ด

มาตรฐาน POSIX นิยาม API สำหรับเข้าถึงฐานข้อมูลบนไฟล์ที่รู้จักในชื่อ
[DBM](https://web.archive.org/web/20210105035602/https://www.mankier.com/0p/ndbm.h)
เป็นตัวอย่างชั้นเยี่ยมของ API แบบ "อิงออบเจกต์"

นี่คือนิยามในภาษา C ซึ่งหวังว่าจะอ่านง่ายสำหรับผู้ที่ทำงานกับ FFI ความเห็นด้านล่างจะช่วยอธิบายสำหรับผู้ที่อาจไม่ทันสังเกตความละเอียดอ่อน

```C
struct DBM;
typedef struct { void *dptr, size_t dsize } datum;

int     dbm_clearerr(DBM *);
void    dbm_close(DBM *);
int     dbm_delete(DBM *, datum);
int     dbm_error(DBM *);
datum   dbm_fetch(DBM *, datum);
datum   dbm_firstkey(DBM *);
datum   dbm_nextkey(DBM *);
DBM    *dbm_open(const char *, int, mode_t);
int     dbm_store(DBM *, datum, datum, int);
```

API นี้กำหนดสองชนิดข้อมูล: `DBM` และ `datum`

ชนิด `DBM` ถูกเรียกว่าชนิด "encapsulated" ข้างต้น มันออกแบบมาเพื่อบรรจุสถานะภายใน และทำหน้าที่เป็นจุดเข้าถึงพฤติกรรมของไลบรารี

มันทึบแสงโดยสมบูรณ์ต่อผู้ใช้ ซึ่งไม่สามารถสร้าง `DBM` ได้เองเพราะไม่รู้ขนาดหรือเลย์เอาต์ของมัน ผู้ใช้ต้องเรียก `dbm_open` ซึ่งให้เพียง*พอยน์เตอร์ไปยังมัน*เท่านั้น

นี่หมายความว่า `DBM` ทั้งหมดเป็น "เจ้าของ" โดยไลบรารีในความหมายของ Rust สถานะภายในที่มีขนาดไม่ทราบแน่นอนถูกเก็บไว้ในหน่วยความจำที่ควบคุมโดยไลบรารี ไม่ใช่ผู้ใช้ ผู้ใช้จัดการวงจรชีวิตของมันได้เพียงด้วย `open` และ `close` และดำเนินการกับมันด้วยฟังก์ชันอื่นๆ

ชนิด `datum` ถูกเรียกว่าชนิด "transactional" ข้างต้น มันออกแบบมาเพื่ออำนวยความสะดวกในการแลกเปลี่ยนข้อมูลระหว่างไลบรารีกับผู้ใช้

ฐานข้อมูลออกแบบมาเพื่อเก็บ "ข้อมูลไร้โครงสร้าง" โดยไม่มีความยาวหรือความหมายที่กำหนดไว้ล่วงหน้า ผลคือ `datum` เทียบเท่ากับสไลซ์ของ Rust ในภาษา C: ไบต์จำนวนหนึ่งกับจำนวนนับว่ามีเท่าไร ความต่างหลักคือไม่มีข้อมูลชนิด ซึ่งเป็นสิ่งที่ `void` บ่งชี้

พึงระลึกว่าเฮดเดอร์นี้เขียนจากมุมมองของไลบรารี ผู้ใช้มักมีชนิดข้อมูลที่ตัวเองใช้อยู่ซึ่งมีขนาดที่ทราบแน่นอน แต่ไลบรารีไม่สนใจ และตามกฎการแปลงชนิดของ C ชนิดใดๆ ที่อยู่หลังพอยน์เตอร์ก็แปลงเป็น `void` ได้

ตามที่กล่าวมา ชนิดนี้*โปร่งใส*ต่อผู้ใช้ แถมยัง*เป็นเจ้าของ*โดยผู้ใช้ด้วย ซึ่งมีผลกระทบละเอียดอ่อนเนื่องจากพอยน์เตอร์ที่อยู่ข้างใน คำถามคือ ใครเป็นเจ้าของหน่วยความจำที่พอยน์เตอร์นั้นชี้ไป?

คำตอบที่ดีที่สุดสำหรับความปลอดภัยด้านหน่วยความจำคือ "ผู้ใช้" แต่ในกรณีอย่างการดึงค่าออกมา ผู้ใช้ไม่รู้วิธีจัดสรรหน่วยความจำอย่างถูกต้อง (เพราะไม่รู้ว่าค่านั้นยาวเท่าไร) ในกรณีนี้ โค้ดไลบรารีต้องใช้ฮีปที่ผู้ใช้เข้าถึงได้ เช่น `malloc` และ `free` ของไลบรารี C แล้ว*ถ่ายโอนความเป็นเจ้าของ*ในความหมายของ Rust

ทั้งหมดนี้อาจดูเป็นการคาดเดา แต่นี่คือสิ่งที่พอยน์เตอร์หมายถึงใน C มันหมายถึงสิ่งเดียวกับใน Rust: "ไลฟ์ไทม์ที่ผู้ใช้กำหนด" ผู้ใช้ไลบรารีต้องอ่านเอกสารประกอบเพื่อใช้งานอย่างถูกต้อง ถึงกระนั้นก็มีการตัดสินใจบางอย่างที่มีผลกระทบน้อยกว่าหรือมากกว่าหากผู้ใช้ทำผิด การลดผลกระทบเหล่านั้นให้เหลือน้อยที่สุดคือสิ่งที่แนวปฏิบัตินี้ว่าด้วย และกุญแจสำคัญคือ*ถ่ายโอนความเป็นเจ้าของของทุกสิ่งที่โปร่งใส*

## ข้อดี

วิธีนี้ลดจำนวนการรับประกันความปลอดภัยด้านหน่วยความจำที่ผู้ใช้ต้องรักษาให้เหลือน้อยชิ้น:

1. อย่าเรียกฟังก์ชันใดๆ ด้วยพอยน์เตอร์ที่ไม่ได้ถูกคืนมาจาก `dbm_open` (การ
   เข้าถึงที่ไม่ถูกต้องหรือความเสียหายของหน่วยความจำ)
2. อย่าเรียกฟังก์ชันใดๆ บนพอยน์เตอร์หลังปิด (use after free)
3. `dptr` บน `datum` ใดๆ ต้องเป็น `NULL` หรือชี้ไปยังสไลซ์หน่วยความจำที่ถูกต้อง
   ตามความยาวที่ประกาศไว้

นอกจากนี้ ยังหลีกเลี่ยงปัญหาการตั้งฉายาพอยน์เตอร์ได้มาก เพื่อให้เข้าใจว่าทำไม ลองพิจารณาทางเลือกหนึ่งอย่างละเอียด: การวนซ้ำผ่านคีย์

Rust ขึ้นชื่อเรื่องอิเทอเรเตอร์ เมื่ออิมพลีเมนต์อิเทอเรเตอร์ โปรแกรมเมอร์จะสร้างชนิดข้อมูลแยกที่มีไลฟ์ไทม์ผูกกับเจ้าของ และอิมพลีเมนต์ trait `Iterator`

นี่คือวิธีที่การวนซ้ำจะทำใน Rust สำหรับ `DBM`:

```rust,ignore
struct Dbm { ... }

impl Dbm {
    /* ... */
    pub fn keys<'it>(&'it self) -> DbmKeysIter<'it> { ... }
    /* ... */
}

struct DbmKeysIter<'it> {
    owner: &'it Dbm,
}

impl<'it> Iterator for DbmKeysIter<'it> { ... }
```

แบบนี้สะอาด เป็นสำนวน และปลอดภัยด้วยการรับประกันของ Rust อย่างไรก็ตาม ลองพิจารณาว่าการแปล API แบบตรงไปตรงมาจะมีหน้าตาอย่างไร:

```rust,ignore
#[no_mangle]
pub extern "C" fn dbm_iter_new(owner: *const Dbm) -> *mut DbmKeysIter {
    // THIS API IS A BAD IDEA! For real applications, use object-based design instead.
}
#[no_mangle]
pub extern "C" fn dbm_iter_next(
    iter: *mut DbmKeysIter,
    key_out: *const datum
) -> libc::c_int {
    // THIS API IS A BAD IDEA! For real applications, use object-based design instead.
}
#[no_mangle]
pub extern "C" fn dbm_iter_del(*mut DbmKeysIter) {
    // THIS API IS A BAD IDEA! For real applications, use object-based design instead.
}
```

API นี้สูญเสียข้อมูลสำคัญชิ้นหนึ่ง: ไลฟ์ไทม์ของอิเทอเรเตอร์ต้องไม่ยาวเกินไลฟ์ไทม์ของออบเจกต์ `Dbm` ที่เป็นเจ้าของมัน ผู้ใช้ไลบรารีอาจใช้มันในทางที่ทำให้อิเทอเรเตอร์อายุยืนกว่าข้อมูลที่มันวนซ้ำ นำไปสู่การอ่านหน่วยความจำที่ยังไม่ถูกเริ่มต้น

ตัวอย่างนี้เขียนในภาษา C และมีบั๊กที่อธิบายไว้ด้านล่าง:

```C
int count_key_sizes(DBM *db) {
    // DO NOT USE THIS FUNCTION. IT HAS A SUBTLE BUT SERIOUS BUG!
    datum key;
    int len = 0;

    if (!dbm_iter_new(db)) {
        dbm_close(db);
        return -1;
    }

    int l;
    while ((l = dbm_iter_next(owner, &key)) >= 0) { // an error is indicated by -1
        free(key.dptr);
        len += key.dsize;
        if (l == 0) { // end of the iterator
            dbm_close(owner);
        }
    }
    if l >= 0 {
        return -1;
    } else {
        return len;
    }
}
```

บั๊กนี้เป็นบั๊กคลาสสิก นี่คือสิ่งที่เกิดขึ้นเมื่ออิเทอเรเตอร์คืนเครื่องหมายสิ้นสุดการวนซ้ำ:

1. เงื่อนไขของลูปกำหนด `l` เป็นศูนย์ และเข้าลูปเพราะ `0 >= 0`
2. ความยาวเพิ่มขึ้น ในกรณีนี้เพิ่มศูนย์
3. เงื่อนไข if เป็นจริง ฐานข้อมูลจึงถูกปิด ตรงนี้ควรมีคำสั่ง break
4. เงื่อนไขของลูปถูกประเมินอีกครั้ง ทำให้เกิดการเรียก `next` บนออบเจกต์ที่ปิดไปแล้ว

ส่วนที่แย่ที่สุดของบั๊กนี้? หากการอิมพลีเมนต์ฝั่ง Rust ระมัดระวังดี โค้ดนี้จะทำงานได้เกือบตลอดเวลา! หากหน่วยความจำของออบเจกต์ `Dbm` ไม่ถูกนำไปใช้ซ้ำทันที การตรวจสอบภายในจะล้มเหลวเกือบแน่นอน ทำให้อิเทอเรเตอร์คืนค่า `-1` บ่งชี้ข้อผิดพลาด แต่เป็นบางครั้ง มันจะทำให้เกิด segmentation fault หรือแย่กว่านั้นคือความเสียหายของหน่วยความจำแบบไร้ความหมาย!

Rust หลีกเลี่ยงสิ่งเหล่านี้ไม่ได้เลย ในมุมมองของมัน มันวางออบเจกต์เหล่านั้นไว้บนฮีปของตัวเอง คืนพอยน์เตอร์ไปยังมัน และสละการควบคุมไลฟ์ไทม์ของมัน โค้ด C ต้อง "ทำตัวดีๆ" เท่านั้น

โปรแกรมเมอร์ต้องอ่านและเข้าใจเอกสารประกอบ API แม้บางคนจะถือว่าเป็นเรื่องปกติใน C การออกแบบ API ที่ดีสามารถบรรเทาความเสี่ยงนี้ได้ API ของ POSIX สำหรับ `DBM` ทำเช่นนั้นโดย*รวมความเป็นเจ้าของ*ของอิเทอเรเตอร์เข้ากับตัวแม่ของมัน:

```C
datum   dbm_firstkey(DBM *);
datum   dbm_nextkey(DBM *);
```

ด้วยเหตุนี้ ไลฟ์ไทม์ทั้งหมดจึงถูกผูกเข้าด้วยกัน และความไม่ปลอดภัยเช่นนั้นจึงถูกป้องกันไว้

## ข้อเสีย

อย่างไรก็ตาม ทางเลือกการออกแบบนี้มีข้อเสียหลายประการซึ่งควรพิจารณาเช่นกัน

ประการแรก ตัว API เองแสดงออกได้น้อยลง กับ POSIX DBM มีอิเทอเรเตอร์เพียงตัวเดียวต่อออบเจกต์ และทุกการเรียกเปลี่ยนสถานะของมัน ซึ่งจำกัดมากกว่าอิเทอเรเตอร์ในแทบทุกภาษา แม้จะปลอดภัยก็ตาม บางทีกับออบเจกต์อื่นๆ ที่เกี่ยวข้องซึ่งไลฟ์ไทม์ไม่เป็นลำดับชั้นเท่านี้ ข้อจำกัดนี้อาจมีต้นทุนมากกว่าความปลอดภัยที่ได้

ประการที่สอง ขึ้นอยู่กับความสัมพันธ์ระหว่างส่วนต่างๆ ของ API อาจต้องใช้ความพยายามในการออกแบบอย่างมาก จุดออกแบบที่ง่ายกว่าหลายจุดมีแพตเทิร์นอื่นที่เกี่ยวข้อง:

- [การรวมชนิดเข้าเป็นตัวห่อ](./wrappers.md) จัดกลุ่มชนิดข้อมูล Rust หลายชนิดไว้
  ด้วยกันเป็น "ออบเจกต์" ทึบแสง

- [การส่งต่อข้อผิดพลาดใน FFI](../../idioms/ffi/errors.md) อธิบายการจัดการ
