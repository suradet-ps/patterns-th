# ใช้ trait ที่กำหนดเองเพื่อหลีกเลี่ยงขอบเขตชนิดที่ซับซ้อน

## คำอธิบาย

ขอบเขตของ trait (trait bounds) อาจกลายเป็นเรื่องเทอะทะได้ โดยเฉพาะเมื่อเกี่ยวข้องกับ trait ตระกูล `Fn`[^fn-traits] และมีข้อกำหนดเฉพาะเกี่ยวกับชนิดผลลัพธ์ ในกรณีเช่นนั้น การเพิ่ม trait ใหม่เข้าไปอาจช่วยลดความยาวของโค้ด กำจัดพารามิเตอร์ชนิดบางตัว และเพิ่มความสามารถในการแสดงออก (expressiveness) ได้ trait เช่นนั้นอาจมาพร้อมกับ `impl` แบบเจเนอริกสำหรับทุกชนิดที่สอดคล้องกับขอบเขตเดิม

## ตัวอย่าง

ลองจินตนาการถึงระบบมอนิเตอร์หรือเก็บรวบรวมข้อมูลสักอย่าง ระบบดึงค่าต่างชนิดจากแหล่งที่มาหลากหลาย อาจอนุมานสถานะบางอย่างจากค่าเหล่านั้นเพื่อบ่งชี้ปัญหา ตัวอย่างเช่น ปริมาณหน่วยความจำว่างทั้งหมดควรสูงกว่าเกณฑ์หนึ่ง และผู้ใช้ที่มี id `0` ควรมีชื่อว่า "root" เสมอ

ด้วยเหตุผลด้านการจัดการ เราคงต้องการ type erasure ที่ระดับบนสุด อย่างไรก็ตาม เรายังต้องมีการประเมินเฉพาะทาง (ที่ผู้ใช้กำหนดได้) สำหรับข้อมูลจากแหล่งชนิดเฉพาะ (เช่น เกณฑ์และช่วงสำหรับชนิดตัวเลข) และเนื่องจากแหล่งที่มาของค่าเหล่านี้หลากหลาย เราอาจเลือกส่งแหล่งข้อมูลเป็นโคลเชอร์ที่คืนค่าเมื่อถูกเรียก เนื่องจากเราคงได้ค่าเหล่านี้มาจากระบบปฏิบัติการ เราจึงมีแนวโน้มต้องเผชิญกับการดำเนินการที่อาจล้มเหลว

เราจึงอาจลงเอยด้วยชนิดและ trait ต่อไปนี้สำหรับจัดการค่าเฉพาะทาง:

```rust
use std::fmt::Display;

struct Value<G: FnMut() -> Result<T, Error>, S: Fn(&T) -> Status, T: Display> {
    value: Option<T>,
    getter: G,
    status: S,
}

impl<G: FnMut() -> Result<T, Error>, S: Fn(&T) -> Status, T: Display> Value<G, S, T> {
    pub fn update(&mut self) -> Result<(), Error> {
        (self.getter)().map(|v| self.value = Some(v))
    }

    pub fn value(&self) -> Option<&T> {
        self.value.as_ref()
    }

    pub fn status(&self) -> Option<Status> {
        self.value().map(&self.status)
    }
}

// ...

enum Status {
    // ...
}

struct Error {
    // ...
}
```

ด้วยชนิดเหล่านี้ เราจะต้องเขียนขอบเขตของ trait สำหรับ `G` ซ้ำอย่างน้อยสองสามที่ ความอ่านง่ายย่อมแย่ลง ส่วนหนึ่งเพราะ getter คืนค่า `Result` การเพิ่มขอบเขตสำหรับ "getter" ช่วยให้ได้ขอบเขตที่แสดงออกได้ดีขึ้นและกำจัดพารามิเตอร์ชนิดตัวหนึ่งออกไปได้:

```rust
# use std::fmt::Display;
trait Getter {
    type Output: Display;

    fn get_value(&mut self) -> Result<Self::Output, Error>;
}

impl<F: FnMut() -> Result<T, Error>, T: Display> Getter for F {
    type Output = T;

    fn get_value(&mut self) -> Result<Self::Output, Error> {
        self()
    }
}

struct Value<G: Getter, S: Fn(&G::Output) -> Status> {
    value: Option<G::Output>,
    getter: G,
    status: S,
}

// ...
# enum Status {}
# struct Error;
```

## ข้อดี

การเพิ่ม trait ใหม่ช่วยลดความซับซ้อนของขอบเขตชนิดได้ โดยเฉพาะผ่านการกำจัดพารามิเตอร์ชนิด ชื่อที่ดีของ trait ใหม่ยังทำให้ขอบเขตแสดงออกได้ชัดเจนขึ้น trait ใหม่ในฐานะนามธรรมยังเปิดโอกาสในตัวเองด้วย เช่น:

- ชนิดเฉพาะทางเพิ่มเติมที่อิมพลีเมนต์ trait ใหม่ (เช่น ชนิดที่แทนเอกลักษณ์บางอย่าง)
  รวมถึง trait ที่มีประโยชน์อื่นๆ เช่น `Default` และ
- เมท็อดเพิ่มเติม ตราบใดที่อิมพลีเมนต์ให้กับทุกชนิดที่เกี่ยวข้องได้

## ข้อเสีย

การเพิ่มรายการใหม่เช่น trait หมายความว่าเราต้องหาชื่อและตำแหน่งที่เหมาะสมให้กับมัน มันยังหมายความว่าผู้ใช้ฟังก์ชันเดิมมีรายการเพิ่มขึ้นให้ต้องศึกษาอีกหนึ่งรายการ[^read-docs] ขึ้นอยู่กับการนำเสนอ อาจไม่ชัดเจนในทันทีว่าโคลเชอร์ธรรมดาสามารถใช้เป็น `Getter` ในตัวอย่างข้างต้นได้

[^fn-traits]: กล่าวคือ `Fn`, `FnOnce` และ `FnMut`

[^read-docs]: หมายความว่าพวกเขาอาจต้องอ่านเอกสารประกอบเพิ่มขึ้น
